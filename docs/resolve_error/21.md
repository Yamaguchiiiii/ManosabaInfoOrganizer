## §A 【症状1 + 最重要1】Canvas のビューポート方針 — 「ウィンドウ基準の fill」を仕様化し、パネル開閉では固定する

### 方針決定（最重要1 への回答）

検討した選択肢:

| 案 | 内容 | 評価 |
|---|---|---|
| A. 全ノートを 1200×800 固定（事件ノートと同じレターボックス） | どの環境でも同じ紙面 | ✕ 既存データが 1200×800 の外に配置され得る（fill 運用で広い画面に置いた分が到達不能になる）。移行で座標クランプするとレイアウトが壊れる |
| B. 現状 fill のまま仕様化のみ | 実装変更なし | ✕ 症状1（パネル開閉のたびに見える範囲が変わる）が残る |
| C. パン/ズーム付き無限キャンバス | 自由度最大 | ✕ 4ペイン・PNG書き出し・「紙」メタファーと相性が悪く、工数過大 |
| **D. fill を仕様化しつつ「論理ビューポートはウィンドウサイズにのみ追従」させる** | 下記 | **◎ 採用** |

**採用仕様（チュートリアルに書く内容そのもの）**:
- 事件ノートのキャンバスは常に **1200×800 固定**（Animate と共有するため）。
- 全体／キャラクター／メモのキャンバスは **「ウィンドウの形」に合わせて紙面が広がる**。端末やウィンドウサイズごとに紙面の縦横比が変わるのは仕様（=ユーザーの言う「表現の個性」）。
- ただし紙面の広さが変わるのは**ウィンドウ自体のリサイズ時だけ**。左パネルの開閉・リサイズなどウィンドウ内の UI 操作では、紙面はそのまま等倍縮小/拡大（不足分は暗色マージン=レターボックス）され、**見えていた範囲が隠れたり、見えなかった範囲が現れたりしない**。← これが症状1の修正。

### 現状

`src/components/note/CanvasWorkspace.tsx`
- ResizeObserver（grep: `new ResizeObserver((entries)`、L206-225）が**コンテナ実寸**を `canvasSize` に入れる。
- ペイン計算（grep: `const useRangeFit = targetType === 'preset'`、L1146-1162）: 非 preset は `stageRenderW = stageWidth`（コンテナいっぱい）＋ `effScale = min(stageW/1200, stageH/800)` → **論理ビューポート = コンテナ寸/effScale**。ContextPanel の開閉（`App.tsx` L157 `{!contextPanelCollapsed && <ContextPanel />}`）でコンテナ幅が変わる → 見える論理範囲が直接変わる（症状1の根）。

## §B 【症状2】ページ遷移: 遷移先が一瞬見えてからフェードが走る

### 原因

`src/App.tsx` `handleTransition`（grep: `const handleTransition = (action: () => void)`、L72-91）。
`setOverlayPhase('visible')` の**次フレームで即 `action()`**（=ビュー差し替え）を実行している。オーバーレイ（`LoadingScreen`）はマウント直後 opacity 0 → 180ms かけてフェードインするため、**その 180ms の間、半透明オーバーレイ越しに遷移先ページが見える**。

### 実装

`action()` の実行をフェードイン完了（`FADE_MS`）後に遅らせる。あわせて `action()` が throw しても遷移ロックが残らないよう try/finally を入れる（revise_bad_implementation2 №A1 と同時解消）:
```tsx
const handleTransition = (action: () => void) => {
    transitionBusyRef.current = true;
    setOverlayPhase('visible');
    // オーバーレイのフェードイン完了後に重い処理（ビュー差し替え）を行う。
    // 旧: 次フレームで即実行 → 遷移先が半透明オーバーレイ越しに一瞬見えていた（0711 #2）
    window.setTimeout(() => {
        const shownAt = performance.now();
        requestAnimationFrame(() => {
            try { action(); } finally {
                requestAnimationFrame(() => {
                    const wait = Math.max(0, MIN_OVERLAY_MS - (performance.now() - shownAt));
                    setTimeout(() => {
                        setOverlayPhase('leaving');
                        setTimeout(() => {
                            setOverlayPhase('hidden');
                            transitionBusyRef.current = false;
                        }, FADE_MS);
                    }, wait);
                });
            }
        });
    }, FADE_MS);
};
```
`MIN_OVERLAY_MS = 250` / `FADE_MS = 200` は既存値のまま。総遷移時間は約 200+250+200ms。

### 受入条件
1. Create⇔Animate⇔Note の全遷移で、**旧ページ → オーバーレイ完全不透明 → 新ページ** の順になり、新ページ内容がフェードイン完了前に見えない（速度 0.25x のブラウザ DevTools アニメーション減速で目視確認）。
2. 遷移ボタン連打で二重遷移しない（`transitionBusyRef` ガード維持）。
3. preview の自動検証はクリック後 800〜1100ms 待ってから DOM を読む。

## §D 【症状4】選択コンテキストバーを ContextBar（Note ▸ … の上部バー）へ統合

## §E 【症状5 + 最重要3】sync: 合流する「相手の訪問」を選択可能にし、実現不能な合流を作らせない

### 最重要3 の事象の明確化（バックアップ解析結果）

`manosaba-backup-20260711-0204.json` の preset「Episode 5」（キャラ名は敬称略）:

|---|---|---|---|
| 二階堂ヒロ | 0 | 2400.0 | なし |

ノアの経路: `wvxf4w0mb` が path index **0, 4, 8**（ヒロとの同行区間）、`q76sd5mlv` が index **16**。
ミリアが `q76s` を通るのは **t=0 の1回だけ**（彼女の開始地点。全行動が t=348.9 で終了）。ノアの `q76s` 自然到達は **t≈1925**。

発生機序:
1. `handleSyncTime`（`useRouteEditor.ts` L346、grep: `const handleSyncTime =`）は相手の全訪問から「自分の自然到達に最も近い訪問」を**自動選択**する。ミリアの訪問は t=0 しか無いので t=0 が選ばれ、`meetingTime = 0` の制約が保存された（**症状5: 訪問を選べない／選択肢も時刻も見えない**。`MergeModal` の表示は「この地点まで約 0 フレームで到達」で異常に気づけない）。
2. 再生時 `computeAnchors`（`animationUtils.ts` L214）はアンカー時刻を単調増加へ**クランプ**する: `if (t <= prevTime) t = prevTime + 1;`（grep: `単調増加クランプ`）。ノアのアンカーは `[開始1185.5] → [q76s: 0→1186.5にクランプ]` となり、**開始直後に 1233px を 1 フレームで移動（通常速度の約740倍=瞬間移動）**。以降の全区間が前倒しされ、終了は本来の 2274 ではなく 1535 になる。ヒロとの同行区間（index 0〜8）も 1 フレームに圧縮され消滅する。
3. さらにイベント一覧には「⚇遭遇 00:00 q76s ノア・ミリア」が表示されるが、**t=0 にノアはそこに居ない**（実際には誰も出会わない偽イベント）。保存時の `validatePresetSync` は「速すぎる移動」warn を出すのみで、保存はそのまま成立していた。

修正は (1) 作成時に訪問を選ばせ・実現不能な選択を防ぐ、(2) 万一データに残っても瞬間移動しない、(3) 保存時検証で error として明示する、の3層で行う。

```ts
// 自分の既存 sync 制約から、今回の地点(myPathIndex)で許される合流時刻の範囲を求める。
// 手前の制約: その時刻 + 通常速度での移動時間より早くは着けない（下限）
// 後の制約:   そこへ通常速度で間に合う時刻まで（上限）
// 最初の sync（既存制約なし）は startTime 側が自由に動くため無制限。0711 最重要3
const spf = MOVEMENT_SPEED_PX_PER_SEC / TARGET_FPS;   // constants から import 追加
const cached = precomputePath(displayPath, nodes);     // animationUtils から import 追加
const idxOfConstraint = (sc: SyncConstraint): number => {
    const occ = sc.occurrence ?? 0; let cnt = 0;
    for (let i = 0; i < displayPath.length; i++) {
        if (displayPath[i] === sc.waypointId) { if (cnt === occ) return i; cnt++; }
    }
    return displayPath.indexOf(sc.waypointId);
};
let lowerBound = -Infinity, upperBound = Infinity;
if (myPathIndex >= 0) {
    syncConstraints.forEach(sc => {
        const i = idxOfConstraint(sc);
        if (i < 0 || i === myPathIndex) return;
        const dist = Math.abs((cached.cumulative[myPathIndex] ?? 0) - (cached.cumulative[i] ?? 0));
        if (i < myPathIndex) lowerBound = Math.max(lowerBound, sc.meetingTime + dist / spf);
        else upperBound = Math.min(upperBound, sc.meetingTime - dist / spf);
    });
}
lowerBoundRef.current = lowerBound;   // E-4 の最終検証用に保持（useRef<number> を2本追加）
upperBoundRef.current = upperBound;

const candidates: MergeCandidate[] = [];
Object.entries(activePreset.data).forEach(([cid, data]) => {
    if (selectedIcons.includes(cid)) return;
    const resolvedStart = resolvedStarts[cid] ?? (data.startTime || 0);

    const visits = getNodeVisitOccurrences(cData, waypointId, nodes);
    if (visits.length === 0) return;
    const occurrences = visits.map(v => ({
        ...v,
        // 到達〜出発（滞在中も合流可）のどこかが実現可能域に入っていれば feasible
        feasible: v.departure >= lowerBound - 0.5 && v.arrival <= upperBound + 0.5,
    }));
    let defaultIndex = -1, bestDiff = Infinity;
    occurrences.forEach((o, i) => {
        if (!o.feasible) return;
        const d = Math.abs(o.arrival - myAbsArrival);
        if (d < bestDiff) { bestDiff = d; defaultIndex = i; }
    });
    candidates.push({ charId: cid, occurrences, defaultIndex, myAbsArrival, data: cData });
});
```

## §I 【症状9】ヘルプが F1 で開かない

### 原因（推定順）

`src/hooks/useTutorial.ts`（grep: `F1 / Shift+/（=?）でヘルプドロワーを開閉`）の listener は bubble 段で、かつ `INPUT/TEXTAREA/SELECT/contentEditable` フォーカス中は F1 も弾く。
1. **SELECT フォーカス残り**: プリセット選択などの `<select>` 操作後はフォーカスが select に残り、F1 が無視される（Shift+/ も無視されるが、`?` を打つ状況=本文入力後が多く再現しにくい）。
2. ブラウザ既定の F1 ヘルプ（Edge/WebView2）との競合は preventDefault で抑止できるが、bubble 段では他リスナーの stopPropagation の影響を受け得る。
3. それでも開かない場合はキーボードの Fnロック（F1がメディアキー）＝環境要因（コードでは対処不能。受入で切り分け）。

### 実装

```ts
useEffect(() => {
    const onKey = (e: KeyboardEvent) => {
        if (e.isComposing || e.keyCode === 229) return; // IME変換中は奪わない
        // F1 は文字入力に使われないため、入力欄フォーカス中でも常に受け付ける。
        // ブラウザ既定のヘルプより先に受けるため capture で listen し、必ず preventDefault する。0711 #9
        if (e.key === 'F1') {
            e.preventDefault();
            setDrawerOpen(o => !o);
            return;
        }
        const t = e.target as HTMLElement | null;
        const tag = t?.tagName;
        if (tag === 'INPUT' || tag === 'TEXTAREA' || tag === 'SELECT' || t?.isContentEditable) return;
        if (e.shiftKey && (e.key === '?' || e.key === '/' || e.code === 'Slash')) {
            e.preventDefault();
            setDrawerOpen(o => !o);
        }
    };
    window.addEventListener('keydown', onKey, true);   // capture
    return () => window.removeEventListener('keydown', onKey, true);
}, []);
```

### 受入条件
1. Create/Animate/Note 各ページで F1 → ヘルプ開閉。**select 操作直後・検索ボックスにフォーカスがある状態でも** F1 で開く。
2. ブラウザのヘルプページ（Edge: Microsoft サポート）が開かない。
3. Shift+/ は従来どおり（入力欄フォーカス中は発火しない）。
4. Web 版と `npm run tauri dev`（WebView2）の両方で確認。それでも NG の環境は preview の `javascript_tool` で `window.addEventListener('keydown', e => console.log(e.key))` を仕込み、F1 押下時にイベント自体が来るかで Fn ロック（ハード側）と切り分ける。

## §J 【最重要2】テキストオブジェクトの複数選択ドラッグ移動

### 原因

複数選択の連動ドラッグは Konva `Transformer` の `_proxyDrag`（node_modules/konva/lib/shapes/Transformer.js: attach されたノードの dragmove で他ノードを `startDrag`）が実現している。しかし `CanvasWorkspace.tsx` の Transformer 同期 effect（grep: `複数選択時はテキストをTransformerから除外`、L427-433）が **Text ノードを Transformer から除外**しているため（複数リサイズでの文字歪み防止・仕様として維持）、テキストは連動対象外 = 複数選択してもテキストだけ動かない/テキスト起点では他が動かない。

### 実装

Transformer の除外は維持し、**自前で startDrag を伝播**する（Konva の `_proxyDrag` と同じ仕組み。`node.isDragging()` ガードで二重開始は起きない）。

**1. `src/components/note/NoteObjectComponents.tsx`** — `NoteObjectComponentProps` に `onDragStart?: (e: Konva.KonvaEventObject<DragEvent>) => void;` を追加し、`URLImage`（KonvaImage と失敗時 Group の両方）/`EditableText`/`ShapeObject` の `commonProps` に `onDragStart` を渡す。

**2. `src/components/note/CanvasWorkspace.tsx`** — オブジェクト props 構築部（grep: `const props = {`、`groupDragHandlers` の直後）に追加:
```tsx
// 最重要2: 複数選択の連動ドラッグ。Transformer の _proxyDrag は attach 済みノード（非テキスト）
// 同士にしか効かないため、(a) 起点が何であれ選択中テキストへ、(b) 起点がテキストなら選択中
// 非テキストへも、startDrag を伝播する。isDragging() ガードで二重開始しない。
onDragStart: (e: Konva.KonvaEventObject<DragEvent>) => {
    if (selectedIds.length < 2 || !selectedIds.includes(obj.id)) return;
    const stage = stageRefs.current[index];
    if (!stage) return;
    objs.forEach(o => {
        if (o.id === obj.id || !selectedIds.includes(o.id)) return;
        // 起点が非テキストの場合、非テキスト同士は Transformer が連動させるので対象外
        if (obj.type !== 'text' && o.type !== 'text') return;
        const node = stage.findOne(`#${o.id}`);
        if (node && !node.isDragging()) node.startDrag(e);
    });
},
```
各ノードは自分の `dragend` で `handleObjectDragEnd`（絶対座標 commit）を通るため、**確定処理の追加は不要**（同一 mouseup 内の複数 dragend は「render 時スナップショット + 絶対座標書き込み」により冪等。さらなる堅牢化は revise_bad_implementation2 №N4）。

既知の見た目上の制限（許容・ドキュメント化のみ）: 複数選択時のテキスト選択破線（grep: `sel_indicator_`）は store 座標由来のためドラッグ中は追従せず、ドロップ確定で追いつく。

### 受入条件
1. テキスト2つをマーキー選択（または Shift+クリック）→ どちらをドラッグしても**両方が一緒に移動**し、確定後に Ctrl+Z 1回で両方戻る。
2. テキスト+図形+画像の混在選択で、**テキスト起点/図形起点どちらのドラッグでも全員が動く**。
3. グループ（Ctrl+G）の従来ドラッグ・ペイン跨ぎ移動（4ペイン編集）・スナップ（⌗）が従来どおり。
4. 単独テキストのドラッグ/ダブルクリック編集に変化なし。
