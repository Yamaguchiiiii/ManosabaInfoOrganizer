## 症状1: Goal未設定なのに経路がハイライトされる ✅

### 根本原因

`useWaypointPath.ts` と `CreateView.tsx` の waypoint 名前解決処理が、
**名前が空文字 `""` の waypoint を、名前が空文字のノードに誤マッチ**させていた。

- `useWaypointPath.ts`: `nodes.find(n => n.name === wp.name)`（`wp.name === ""`）
- `CreateView.tsx` の名前解決 useEffect: 同上

マップ上に `name === ""` のノード（階段・パスノード等）が存在すると、
Goal（空欄）がそのノードの id を取得してしまい、`validPoints.length >= 2` となって
Start→そのノード（=階段など）の最短経路が引かれてハイライトされていた。

### 修正

両箇所で「名前が空ならマッチを試みない」ガードを追加。

- `src/hooks/useWaypointPath.ts`
  ```ts
  if (wp.id !== "") return wp;
  if (!wp.name || wp.name.trim() === "") return wp; // 追加
  const match = nodes.find(n => n.name === wp.name);
  ```
- `src/components/CreateView.tsx`（名前解決 useEffect）
  ```ts
  const trimmedName = wp.name ? wp.name.trim() : "";
  const matchedNode = trimmedName ? nodes.find(n => n.name === wp.name) : undefined;
  ```

## 症状2: Add Stop 後のターゲットを Goal にする ✅

### 根本原因

`handleAddWaypoint` は Goal を新しい中継地点へ移動し Goal を空にするが、
直前に Goal 入力欄へフォーカスしていた場合 `suggestionTargetIndex` が末尾（旧Goal）を指したまま。
配列が伸びると同じ index が **移動後の中継地点** を指すため、次のノードクリックが中継地点に入っていた。

### 修正

`src/components/CreateView.tsx` `handleAddWaypoint` で、追加後の新Goal（末尾）を明示的にターゲット。
追加前の `waypoints.length`（=新Goalの index）を使う。
```ts
setSuggestionTargetIndex(waypoints.length);
```

## 症状5: 開始時の無駄な待機時間を除去 ✅

### 根本原因

`useAnimationPositions.ts` はアニメ時刻 `timeRef` を 0 から進めるが、
複数Syncの結果すべてのキャラの `startTime` が正に押し上げられると、
`currentTime ∈ [0, min(startTime))` の間は全員が始点で待機し、無駄な空白時間になる。
`startTime` の最小値を 0 に揃える正規化が無かった。

### 修正

全キャラの `startTime` 最小値 `offset`（>0 のときのみ）を全員から引いて正規化。
全員同じ offset でシフトするため Sync の相対時間差は不変。表示用キャッシュのみで永続データは変更しない。

- `src/hooks/useAnimationPositions.ts`: プリセット変更 useEffect で `offset = min(startTime)` を算出し
  正規化済み `charData` を `pathCacheRef` に格納、`maxDurationRef` も正規化後で算出。
- `src/components/AnimationTimeline.tsx`: スライダー長 `maxDuration` も同じ offset で正規化し、
  アニメーション実体とタイムラインの長さを一致させる。

### 注意

`startTime` が負（t=0 時点で既に移動中の設計）のキャラがいる場合は `offset=0` とし挙動を変えない
（無駄待機は最小値が正のときのみ発生するため）。

## 症状3: 同一地点の複数回訪問を時系列順に扱う ✅

### 実装結果（2026-06-20）

`CreateView.tsx` の `handleMergeConfirm` で、FollowConfirmModal の「〜まで同行」候補
（`subsequentWaypoints`）を **オカレンス順** に解決するよう修正。

- `resolveWaypointPathIndices(path, waypoints)` を追加。waypoint を訪問順に走査し、
  直前の出現位置以降から次の出現を探すことで、同一地点が複数回出る経路でも
  正しい時系列インデックスを得る（`indexOf` 先頭固定問題を解消）。
- 同名地点が複数回出る場合は表示名に `（n回目）` を付与（`FollowWaypoint.displayLabel`）。
- 候補は `pathIndex` 昇順で並べ、合流地点（候補の最初の訪問）より後のものを提示。

**残存制限:** 合流の到達時刻計算 `calculateNodeArrivalTime` は依然として候補の
「最初の訪問」基準（`indexOf`）。候補の2回目訪問**そのものに合流時刻を合わせる**には
オカレンス指定版の到達時刻計算とUI追加が必要で、本対応の範囲外（表示順の改善に留める）。

---

### 旧・設計メモ（参考）

### 根本原因

Sync/Follow のロジックが node id ベースで `path.indexOf(id)`（=最初の出現）を使っている。

- `CreateView.tsx` `handleMergeConfirm`:
  - `targetPath.indexOf(mergeTargetWaypointId)` → 同一地点を2度通る経路では1回目しか取れない
  - `subsequentWaypoints` 抽出も `targetPath.indexOf(wp.id)` で1回目基準
- `animationUtils.calculateNodeArrivalTime`: `path.indexOf(targetNodeId)` で1回目の到達時刻のみ

そのため「地点X(2回目)」をSync対象/同行候補として時系列順に提示できない。

### 修正方針

waypoint を「node id」ではなく「**訪問オカレンス（node id + 何回目か）**」で識別する。

1. `MergeCandidate` に、その地点を通る各オカレンスの `pathIndex` と到達時刻の配列を持たせる。
   `calculateNodeArrivalTime` を拡張し、`targetPathIndex` を引数に取る版
   `calculateArrivalTimeAtIndex(charData, pathIndex, nodes)` を追加（`indexOf` ではなく与えられた index で距離積算）。
2. `handleSyncTime` 候補生成時、対象地点の **全オカレンス** を列挙し、
   「地点X(1回目) / 地点X(2回目)…」を時系列（pathIndex 昇順）で MergeModal に提示。
3. `MergeModal` の候補表示に「(n回目)」ラベルと到達時刻を表示。`onConfirm` は選択した
   `{charId, pathIndex}` を返すよう変更。
4. `handleMergeConfirm` / `FollowConfirmModal` の `subsequentWaypoints` 抽出を pathIndex 基準にする。

### 影響ファイル

`CreateView.tsx`, `modals/MergeModal.tsx`, `utils/animationUtils.ts`

### 実装上の注意

`indexOf` を pathIndex 受け渡しに置き換える箇所が広い。Sync の根幹ロジックのため、
単純Sync（1回訪問）の既存挙動を壊さないこと（pathIndex 未指定時は従来の最初の出現にフォールバック）。

## 症状6: 未保存経路の遷移ガード ✅

### 実装結果（2026-06-20）

- `services/navigationGuard.ts`: ガード関数を登録/実行するシングルトンレジストリを新規作成
  （`setNavigationGuard` / `runNavigationGuard(): Promise<boolean>`）。
- `CreateView.tsx`: `hasUnsavedPath = isEditing && displayPath.length > 0` の間だけ、
  `showDialog`（保存して移動 / 保存せず移動 / キャンセル の3択）を返すガードを登録。
  「保存して移動」は既存 `handleSavePath` を再利用。アンマウント/保存時に解除。
- `App.tsx`: 単一キャラ切替（`handleIconSelect` 非Shift）とモード切替
  （`changeModeWithTransition`）の前に `await runNavigationGuard()` を実行し、
  キャンセル時は遷移を中止。同一キャラ再選択・Shift複数選択・フロア切替は対象外。

### 旧・設計メモ（参考）

### 現状

`CreateView` の編集状態（`isEditing` + 未保存の `waypoints`/`startTime`/`syncConstraints`）は
ローカル state。キャラ切替（`primaryIcon` 変更 useEffect で破棄）、モード変更・フロア変更
（`App.tsx`）、サイドバー操作時に、確認なしで編集内容が失われる。

### 修正方針

1. 「未保存変更あり」フラグを判定（`isEditing && displayPath.length > 0 && 未保存`）。
2. 遷移を試みる操作（アイコン選択・モード/フロア変更）を **インターセプト**し、
   未保存ならオーバーレイ（症状4の基盤を流用）で
   「このキャラクターの行動を保存しますか？ [保存して移動 / 保存せず移動 / キャンセル]」を提示。
3. 実装案: pending な遷移アクションを保持するガード。
   - `CreateView` に「未保存か」を App へ伝える仕組み（コールバック登録 or store フラグ）を追加。
   - `App.tsx` の `handleIconSelect` / `changeModeWithTransition` / `changeFloorWithTransition` で
     未保存なら遷移を保留し確認ダイアログを表示、結果に応じて `handleSavePath` 実行 or 破棄してから遷移。

### 影響ファイル

`App.tsx`, `CreateView.tsx`, `Sidebar.tsx`（遷移トリガ）, ダイアログ基盤（症状4）

### 実装上の注意

- 症状4のダイアログ基盤に依存するため、**症状4を先に実装**する。
- 「保存して移動」は既存 `handleSavePath` を再利用。
- キャラ切替を破棄する `primaryIcon` 変更 useEffect より前にガードを挟む設計が必要
  （現状は selectedIcons 変更が即 useEffect を発火させるため、選択変更自体を保留する必要がある）。
