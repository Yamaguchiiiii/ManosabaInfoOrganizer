## 最優先A: 右下Canvasが点線背景しか出ない ✅（原因特定・修正済み）

### 根本原因

ユーザー報告「右下のCanvasが背景の点線しか表示されない」で確定。
右下セルは `<div className="grid-cell control-cell-wrapper">`。
`.grid-cell` には方眼風の**点線 `background-image`（SVG）**が設定されており、
`.control-cell-wrapper` は `background-color` を `#252526` に上書きしているが
**`background-image` は上書きしていなかった**ため、点線パターンが残っていた。
さらに 22:46 #7 で `NotesPanel`（キャンバス）を撤去した後、`AnimationTimeline`（操作盤）は
**薄い操作バー1本ぶんの高さしか占めず**、セルの大半が空 → そこに点線だけが見えていた。
（3枚のマップは正常表示。Aは「右下セル」限定の問題だった。）

### 修正

- `styles/AnimateView.scss`: `.control-cell-wrapper` に `background-image: none;` を追加し
  点線を打ち消し。`.timeline-section` を `display:flex; flex-direction:column` にして
  操作盤が縦に充填できるようにした。
- `components/AnimationTimeline.tsx`: ルートを `height:100%` + `justify-content:center` にして
  セル全体（暗色 #222）を埋め、操作群を縦中央に配置。`flex-wrap` で狭幅でも崩れないように。

これで右下セルは「点線の空白」ではなく、暗色の操作パネルとして表示される。

## 症状1: 行動なしキャラの待受sync ✅（重複は要検証）

### 根本原因

`handleSyncTime` は `displayPath` から到達時刻を計算する。Goal未設定（Startのみ）だと
`useWaypointPath` は `validPoints<2` で空パスを返し、`calculateNodeArrivalTime` が
`null` → 「到達時刻を計算できませんでした」で停止していた。

### 修正（`CreateView.tsx`）

`myTime === null` かつ `displayPath.length < 2` の場合、その地点に静止して相手を
待ち受けるキャラとみなし、到達時刻＝現在の `startTime`（Delay）として続行する。
これで B の通る地点を Start に入れて sync し、合流させられる。

### 残課題（要live検証）

進捗メモの「同行を選ぶと Goal と同じ地点が重複追加される」件は、追従確定処理
（`FollowConfirmModal` の `onConfirm`）で **合流地点と一致する先頭の追従地点を除外**
するガードを追加して防止した（#5と同じ箇所）。実機で重複が消えるか要確認。

## 症状4: 4ペイン間をまたぐドラッグ移動 ✅（要live検証）

### 難点

各ペインは**独立した Konva `Stage`**（`overflow:hidden`）。Konva のドラッグは
Stage 内に閉じるため「ノードがそのまま別 Stage に乗り移る」ことはできない。
そこで **ドロップ位置のヒットテストで論理的に付け替える**方式を採用した。

### 実装（`NoteView.tsx`）

- 4つのペイン `div` に `paneRefs`（ref配列）を付与。
- 全オブジェクトの `onDragEnd` を統一ハンドラ `handleObjectDragEnd(e, obj, index, scale)` に集約
  （従来のグループ用 `onDragEnd` と単体のデフォルトを統合。`onDragMove` の追従はグループのみ維持）。
- グリッド編集モード中のドロップ時、`e.evt.clientX/Y` が `paneRefs` のどの矩形内かを判定。
  別ペインなら `canvasIndex` を移動先へ更新し、論理座標 `x,y` を
  `(clientX - rect.left - border) / scale` で再計算（グループは全メンバーを平行移動して付け替え）。
- 同一ペイン内は従来どおりの移動として確定。

### 要確認

実機で「Canvas1のオブジェクトをCanvas3へドラッグ→Canvas3に移る」こと、グループごと移ること、
座標ズレが許容範囲か。Konva の dragend が `e.evt`（mouseup）を持つ前提（通常満たす）。

## 症状5: 少し後をついていく（delay） ✅（要live検証）

### 実装（`CreateView.tsx`）

`stayTime`（待機）は `useWaypointPath` で「その地点到達後に出発を遅らせる」滞在として
パスへ反映される（合流地点での arrival 自体は変わらない＝syncは維持される）ことを利用。

- `FollowConfirmModal` に「少し後をついていく（遅延）: __秒」入力を追加
  （同行先を選んだときのみ活性、デフォルト0）。
- 追従確定時、合流地点（追加直前の末尾 waypoint）の `stayTime` に `delaySec` を加算。

  より後ろに挿入されるため、既存 sync のアンカー時刻はずれない。

### 要確認

実機で「遅れて追従」する見た目になるか、複数syncと併用してアンカーがずれないか。

## 最優先B 続報: アニメ「カクツキ」徹底分析

> 正規化のピンポイント復元では直らなかったため正規化は**再実装（元に戻した）**。
> 改めてカクツキ（frame stutter / OOM, 元は `_symptoms 05/16_15:00 #1`）の真因を分析した。

### 結論サマリ
1. **22:46 バッチ（506914e）はアニメ再生のフレーム経路に一切触れていない**（下記証拠）。
   よってフレームレートのカクツキの原因では**ない**。
2. カクツキの真因は**描画コスト**（影付きアイコンの毎フレーム再描画 ＋ 動きの有無に関わらず
   毎フレーム全ノード更新で3レイヤー再描画 ＋ 毎フレームのオブジェクト生成によるGC圧）。
   これは `05/16` からの**既存のChrome性能問題**で、22:46 とは独立。
3. 副次的に、22:46 #1（sync drift 修正）は保存される `startTime` を変えるため、
   **データ起因で「動きが間延び/飛び飛び」に見える**可能性はある（frame stutterとは別物）。
4. 高速再生（speed ≥ 4x）では**seek誤検出による巻き戻り**で激しくカクつく別バグあり。

### 22:46 を精査した結果（再生経路に非接触の証拠）
- `AnimateView.tsx`: `NotesPanel` 撤去の2行のみ。再生ロジック無関係。
- `store.ts`: `isSkullMode` / `addNoteObjects` / プリセット名・rehydrate移行のみ。
  いずれも再生ループ（`useAnimationPositions`）は**購読していない**。
- `animationUtils.ts`: `calculateNodeArrivalTime`（→ラッパ化）/ `calculateArrivalTimeAtIndex` 追加のみ。
  これらは Create の sync 計算用。**再生が使う `precomputePath` / `calculateRawPositionCached` /
  `getCollisionOffsets` は不変**（差分hunkは line 334+ で、これら関数の外）。
- `AnimateView.scss`: 右下セルのみ。
- 再生中、`currentTime` を購読するのは `AnimationTimeline`（30フレーム間引き）だけで、
  **`AnimateView` は再生中に再レンダリングされない**（購読は presets/activePresetId/nodes のみ）。

### フレームレート由来カクツキの真因（最有力・既存問題）
`useAnimationPositions` の単一RAFループは毎フレーム:
1. **影(`shadowBlur:6`)付きアイコンを再描画**（`MovingCharIcon`、機能14で影を追加）。
   Chromeの2D canvas 影描画は重く、「Edge/Tauriは滑らか・Chromeはカクつく」と整合。
2. **動いていないフロア/キャラも含め 15アイコン×3フロア=45ノードに `x/y/visible` を毎フレーム設定**
   → 3つの動的レイヤーが毎フレーム再描画される（変化がなくても）。
3. **毎フレーム `currentVisualPositions[icon] = { x, y, floor }` を新規生成**（最大~900個/秒）
   → GC圧→周期的なジャンク。
4. **一時停止中もRAFが回り続け**、上記のノード更新を継続。

### OOM について
- 22:46 #7 で `NotesPanel`（余分なcanvas）を撤去したため、OOM要因はむしろ軽減方向。
- 再生ループに無制限増加は見当たらない（`history`/`noteHistory` は上限cap、refキーは固定数）。
  残るのは上記の高アロケーションによるGC。

### 高速再生時の巻き戻りカクツキ（別の確定バグ）
- 定数: `ZUSTAND_WRITE_INTERVAL = 4`（currentTimeは4フレームに1回だけ書込）、`SEEK_THRESHOLD = 10`。
- `playbackSpeed ≥ 4x` だと4フレーム間に `timeRef` が10超進む → **誤シーク検出** →
  `timeRef` を古い `storeTime` へ巻き戻し → 毎4フレームでジャンプ。1x/2xでは無害。

### 推奨対策（要live検証・効果が大きい順）
1. **アイコンの影を軽量化/除去**、または動かないキャラを静的レイヤーへ（影の毎フレーム再描画を排除）。
2. **変化のあったフロア/キャラのみ更新**し、変化なしフロアのレイヤー再描画をスキップ。
3. `currentVisualPositions` を**インプレース更新**（毎フレームのオブジェクト生成をやめる）。
4. **一時停止中はノード更新をスキップ**。
5. seek閾値を再生速度に連動させる（または書込間隔を詰める／閾値を上げる）。

### 追加で判明した症状（ユーザー報告）と確定診断
- 「バー上で1秒進めるのに約2.5秒かかる」＝実効再生が約0.4倍速。
- 「キャラが少し前進→少し後退を繰り返し前後に小刻みにカクカク」＝**毎フレーム前進→巻き戻りの振動**。
- **全速度で発生**（高速再生固有ではない）。

これらから、主因は **seek誤検出のフィードバックループ** と確定:
`currentTime` を 4 フレームに 1 回しか書かない一方、`Math.abs(timeRef - storeTime) > 10`
で「外部シーク」を判定していた。低fps時は1フレームの時間進行が大きく、自分の書き込み遅延が
10 を超える → 誤シーク → `timeRef` を**過去の storeTime へ巻き戻し**＋ `lastTs=null` で次フレームの
進行をスキップ。これが「前後の振動」と「進みが遅い（0.4倍）」の両方を生んでいた。
低fps自体は描画コスト（影＋毎フレーム全レイヤー再描画）が原因で、両者が悪循環していた。

### 実施した修正（4点）

1. **seek誤検出の除去（核心）** — `useAnimationPositions.ts`
   `lastWrittenTimeRef` を新設し、「**自分が最後に書いた値**と storeTime のズレ」だけを
   外部シーク（スライダー/ループ折返し/プリセット切替）とみなすよう変更。自分の throttled
   書き込み遅延では発火しなくなり、巻き戻し振動と進行スキップが解消。
2. **毎フレーム全レイヤー再描画の抑止** — `useAnimationPositions.ts`
   ノードの `x/y/visible` を**変化時のみ set**。特に各 icon は常時2フロア分が非表示で、
   旧実装は毎フレーム `visible(false)` を呼んで3レイヤーを毎フレーム dirty 化＝全再描画していた。
   ガードにより「動いていないフロアのレイヤーは再描画されない」。
3. **影の除去＋画像2枚重ねの解消** — `AnimateView.tsx`（`MovingCharIcon`）
   `shadowBlur`（Chromeで高コスト）と画像の二重描画をやめ、1枚＋白縁ストロークのみに。
   レイヤー再描画1回あたりのコストを削減。
4. **毎フレームのオブジェクト生成排除** — `useAnimationPositions.ts`
   `currentVisualPositions[icon]` をインプレース更新（GC圧の軽減）。

> seek閾値・delta上限（`Math.min(delta,100)`）は据え置き。#2/#3 でfpsが上がれば 100ms 上限は
> 通常発火しないため、実機でなお遅い場合のみ上限緩和を検討する。

### live検証結果（ユーザー）
- **Chrome / Tauri(WebView2)＝非常に滑らか**。前後振動・スロー再生は解消。
- **Edgeブラウザのみ、わずかにカクツキが残る**。

### Edge残カクツキの追加分析と修正
重要な観察: **Tauri は WebView2（＝Edge/Chromium エンジン）で動いており、それは滑らか**。
つまり描画コードは Edge エンジン上で十分高速。残るのは **Edge ブラウザ固有の余力不足**
（効率モード/拡張/多タブ/テレメトリ等でCPUヘッドルームが小さく、わずかなフレーム落ちが出やすい）。
そこで「1フレームあたりのコストをさらに下げる」「フレームが落ちても滑らかに見せる」2点を追加:

1. **アイコンの Konva `cache()`（ビットマップ化）** — `AnimateView.tsx`
   画像＋角丸クリップ＋白縁ストロークを一度だけラスタライズ。以降のレイヤー再描画は
   ビットマップのコピーだけになり、毎フレームの画像デコード/クリップ/ストロークを排除。
   `pixelRatio` は `min(devicePixelRatio,2)` で高DPIでもボヤけないよう調整。
2. **追従(LERP)を時間ベース化** — `useAnimationPositions.ts`
   従来は毎フレーム固定 `0.15` 追従＝フレームレート依存。`1 - exp(-LERP_RATE·dt)` に変更し、
   実フレーム間隔 `dt` に応じた追従にした（60fpsで従来同等、フレーム落ち時はその分多く追従）。
   可変フレームレートでも体感の滑らかさを保つ。

> いずれも描画/動きの最適化で、ロジック（時刻・sync）には非干渉。Edgeブラウザの効率モード等の
> 環境要因そのものは変えられないが、コスト削減＋フレーム落ち耐性で実用上の滑らかさを底上げする。

## 追加対応 3-2: 複数/複雑Syncの時刻ズレ（相手キャラ側オカレンス対応）

> `resolve_error/11` 症状1・`_symptoms 05/20 #1` の残課題。自分側アンカーはオカレンス対応済みだったが、
> **相手キャラ側の到達時刻が `indexOf`（最初の訪問）固定**のままだった。

### 問題

同一地点を複数回通る相手キャラに sync する際、合流に使う到達時刻・移動時間が常に
「最初の訪問」基準だったため、A→B→C→D のような引き渡し（同じ地点を複数回経由）で
合流時刻がずれ、別の sync 制約も巻き添えでずれていた。

### 修正

- `utils/animationUtils.ts`: `getNodeArrivalOccurrences(charData, nodeId, nodes)` を新設。
  その地点を通る**全ての訪問**の `{ pathIndex, arrival(絶対時刻) }` を返す（距離は1回だけ計算）。
- `CreateView.tsx` `handleSyncTime`: 各候補キャラについて全訪問を取得し、
  **自分の自然な絶対到達時刻 `startTime + myTime` に最も近い訪問**を合流点に選ぶ。
  「最も近い訪問」は startTime のシフト量 `|meetingTime - arrival|` を最小化＝相手の他予定を壊しにくい。
  選んだ訪問の `pathIndex` を `MergeCandidate` に保持。
- `handleMergeConfirm`: 同行範囲（subsequentWaypoints）の基準を `followTarget.pathIndex`
  （選んだ訪問）に変更。これで「合流地点以降の経由地」が正しい訪問以降だけになる。
- 併せて、待受sync(#1)の `myTime` フォールバックを `startTime`→`0` に修正
  （`myTime` は相対移動時間。静止キャラは 0 が正しく、絶対到達時刻は `startTime + 0`）。

### 影響範囲

- **その地点を1回しか通らないキャラは従来と完全に同一挙動**（occurrences が1件なら indexOf と同値）。
- 変化するのは複数回通るキャラのみ。型・ビルドは通過。**実機での複雑Sync挙動は要検証**
  （例: `_symptoms 05/20 #1` の A→B→C→D 引き渡しで各合流時刻が保たれるか）。
